# 研究问题与最小实验

更新日期：2026-10-23。以下为研究者基于文献与数据特征提出的假设，不是作者原话；当前定位是 constrained semantic TRSSQ，独立新颖性尚未证明。

## 2026-10-22 实测更新

- **RQ1 已获得肯定证据**：6 城、63k 用户、1 年窗、无空间约束时精确扫描 99.6 ms/查询（10.0 qps）；加 50 km bbox 后 34.4 ms（29.1 qps）。单城 6.9k 用户时精确扫描仍 <20 ms，说明规模与空间约束共同决定瓶颈。
- **RQ2 的部分机制已验证**：时间分季度 + 城市分区的 HNSW 候选生成 + 精确 DTW 验证，在 50 km workload 达到 93.25 qps、Recall@10 0.9522、p95 24.5 ms；但尚未实现段级 sketch 或可证明下界，当前贡献是“分区 + 候选排序 + early abandon”，不是序列索引理论。
- **RQ3 仅做了固定计划消融**：城市/季度分区、topn、cand、ef 的交叉点已测；没有实现代价模型或自适应计划。
- **RQ4 未做**：还没有真实领域查询或合作者访谈；查询仍是采样 episode。
- **文献边界已收缩**：GTRSS/TRSSQ 已覆盖连续子轨迹、每轨迹一个代表片段和全局 top-k；Quantum Range Query 已覆盖轨迹段时空范围访问。RQ1–RQ3 必须相对 `hard filter → TRSSQ` 检验，不能把 episode 输出本身写成贡献。

## RQ1：时间窗约束的 episode 检索是否构成系统瓶颈？

**问题**：在真实用户级签到轨迹上，给定短语义 episode、绝对时间窗与空间范围，精确 top-k 是否已经被“时间/空间过滤 + 全扫描 DTW”充分解决，还是仍需要新的序列索引？

**现有不足（待完整查重）**：GTRSS/TRSSQ 已支持每条轨迹的 representative subtrajectory top-k，TISIS* 支持 POI embedding + LCSS，ST2Vec 支持时空软相似度；尚未核到同一系统把绝对时间窗、持续时间与空间范围作为硬可行性，再按稠密语义序列排序。真正待测的是联合执行是否优于 `hard filter → exact/approximate TRSSQ`。

**可检验假设 H1**：当时间窗选择性较高（如 1 天）且空间范围较小时，过滤 + 扫描的 P95 已低于 10 ms，索引收益有限；当时间窗放宽到 1 个月/1 个季度，或数据规模扩大到 10^5–10^6 轨迹时，序列 sketch 剪枝能显著减少 DTW 计算。

**最小实验**：
- 数据：Massive-STEPS New York 用户级轨迹（6,929 条，272,368 签到）；Istanbul/Jakarta 作为扩展。
- 查询：1,000 条采样 episode，长度 3–6，来自不同用户/日期；时间窗取 1 天、1 周、1 月、1 季；空间范围取无约束、5 km、2 km。
- 基线：全扫描 DTW oracle、`hard filter → exact TRSSQ`、GTRSS/TRSSQ 适配、ETQ-embedding、TISIS*-LCSS、整轨迹 ST2Vec/均值 kNN + verify、当前点级 ANN + episode verify。
- 指标：Recall@10、P50/P95、候选数、DTW 次数、索引字节。
- 判定：若所有宽松窗口下全扫描 P95 < 10 ms，RQ1 不成立，应转向更难的查询（多用户/跨城市/流式）。

**风险**：NY 数据只有 6.9k 用户，规模不足以体现索引收益；需要 Istanbul（23.7k 用户）或合成放大。时间窗过滤本身可能把候选降到很少，使问题退化。

## RQ2：多粒度时间分段 + 语义 sketch 能否安全剪枝？

**问题**：能否为每条轨迹建立多粒度时间分段（如 6h/1d/1w）和段级语义 sketch，使得 sketch 距离构成 DTW/LCSS 的可证明下界，从而在不漏掉精确 top-k 的前提下跳过大部分候选？

**候选机制**：
- 段级 sketch：段内 embedding 的均值、范数范围、首尾向量、类别集合。
- 下界：对 DTW，利用均值差与路径长度导出下界；对 LCSS，利用类别集合交集/embedding 覆盖导出上界。需要证明并实测紧致度。
- 查询计划：先按时间/空间裁剪候选段，再用 sketch ANN 找候选，最后在原始点上验证 DTW。
- 多粒度：查询 duration 决定使用哪一级段，避免过细/过粗。

**可检验假设 H2**：在相同 Recall@10（相对精确 top-k）下，sketch 剪枝把 DTW 验证次数降低至少 5×，端到端 P95 降低至少 2×；索引字节不超过原始轨迹 embedding 的 1.5×。

**最小实验**：在 RQ1 的 workload 上实现离线 sketch 索引（先不做图，暴力 sketch 距离即可），测剪枝率、下界紧致度、召回与延迟。若暴力 sketch 都不能减少验证次数，则图索引也不会。

**风险**：DTW 的下界可能很松；时间窗已经裁剪掉大部分候选，sketch 收益叠加有限。需要区分“时间过滤收益”与“序列剪枝收益”。

## RQ3：时空属性应如何参与执行计划，而不是只做后过滤？

**问题**：给定轨迹谓词、时间窗、空间范围、向量 sketch 和可用索引，如何选择执行顺序与物化粒度，使端到端代价最小？

**候选机制**：
- 代价模型：候选基数估计（时间窗内轨迹数、空间范围内点数、类别/向量选择性）、每候选验证成本、sketch 查询成本。
- 计划空间：时间优先、空间优先、sketch 优先、倒排优先、混合；小候选直接扫描。
- 与现有过滤 ANN 的位图执行对比：位图适合单对象谓词，不适合序列；计划器需要识别这一点。

**可检验假设 H3**：在时间窗/空间范围/查询长度变化时，固定计划会出现 >3× 的 regret；基于候选基数与验证成本的计划器能把 regret 控制在 1.3× 以内（相对实测最优计划）。

**最小实验**：先实现 3–4 个固定计划，测不同选择性下的交叉点；再加入简单代价模型。不要先做复杂学习型优化器。

**风险**：计划器可能只是工程集成；必须用消融证明收益来自时空语义，而不是常数优化。

## RQ4：跨领域查询是否有实际价值？

**问题**：交通/城市/旅游/共享出行领域的分析者是否真的需要“相似 episode”检索？他们当前的替代方法是什么（手工筛选、聚类、DTW 全扫描、SQL + GIS、商业 BI）？查询语义是否需要领域特定的时间/空间约束（通勤、周末、季节、事件窗口、服务区）？

**具体应用假设（待验证，不是已成立结论）**：

- H4a（交通分析）：分析者会用“同城、同季节、相似活动序列”的 episode 对比出行模式；当前替代方法是按日期/区域筛选后人工看轨迹或跑聚类，难以定位“哪一段”相似。
- H4b（行程推荐）：用户愿意用一段历史行程检索相似行程，且返回的具体 episode 时间区间比单一相似度分数更有用。
- H4c（共享出行）：路线匹配需要同时满足时间窗与语义停靠点相似，当前几何路线匹配不能表达“活动类型相似但路径不同”。

**最小验证**：
- 与 2–3 位 mobility/urban/transportation 方向研究者或从业者做半结构化访谈；问题包括：最近一次“找相似行程”的需求是什么？时间/空间窗口如何确定？失败时如何发现？当前用什么工具？返回结果需要哪些可解释字段？
- 收集 5–10 个真实查询，映射到本定义；记录无法表达的约束（如“同一天气”“同一交通方式”“避开某区域”）。
- 用真实查询替换部分采样查询，报告可解释性与领域接受度；若真实查询不需要 episode 定位，则收缩问题。

**验收**：至少 5 个真实查询可以映射到本定义，且领域合作者认为返回的 episode 区间/候选集比现有替代方法更有用；否则不把应用价值写进论文主张。

**风险**：没有领域合作者时，只能做采样 workload；论文的应用价值主张会弱。用户可协助联系合作方或提供领域查询日志。

## 优先级

1. RQ1（必须先做；决定问题是否成立）。
2. RQ2（核心索引贡献；在 RQ1 成立后）。
3. RQ3（系统贡献；在 RQ2 有稳定收益后）。
4. RQ4（并行进行；决定论文的应用叙事）。
