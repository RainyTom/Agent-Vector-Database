# 基线方案（v3）：标准做法，不追求最强

更新日期：2026-10-24。对象是[问题定义 v4](problem-definition.md)。

本文只给出**标准基线**：每个基线实现一种直觉上的标准做法，用默认参数，不做逐查询调参，不自建复杂剪枝。目的是给主体方案提供参照系，而不是与主体方案争夺最优。主体索引/算法另文定义。

## 1. 原则

1. **基线 = 标准实现**。只实现其名字对应的做法：先时间、先空间、先向量、先约束。不叠加代价模型、不混合多种索引、不做逐查询自适应。
2. **参数默认**。每个基线只在一小组固定参数上取最好结果，网格对所有方法相同；不允许为某个基线单独调参。
3. **同一后端**。所有向量候选生成用同一个 ANN 实现与同一组默认参数；所有验证用同一份精确代码与同一 $D/m$。
4. **不造稻草人**。虽然不追求最强，但必须是实践中的自然做法；报告每个基线的最好结果，而不是最差配置。
5. **不与主体方案抢戏**。任何“看起来像论文贡献”的机制（新索引、下界证明、过滤感知遍历、逐查询计划选择）都不进入基线。

## 2. 谓词结构（为什么只有这几种顺序）

四个约束中，时间窗与空间范围对段可分解，可以下推到段级；持续时间与段数只依赖 episode 端点，不可分解。

$$
P_W(E)\iff\bigwedge_{k=u}^{v}P_W(\sigma_k),\qquad
P_R(E)\iff\bigwedge_{k=u}^{v}P_R(\sigma_k),
$$

$$
P_\Delta(E)=\bigl\lvert (t^{e}_v-t^{s}_u)-\Delta_Q\bigr\rvert\le\delta_\Delta,
\qquad
P_m(E):\ v-u+1\ge m .
$$

因此标准做法只有四种顺序：先时间、先空间、先向量、先约束。持续时间与段数在拿到候选端点后统一检查，不单独构成基线。

## 3. 基线列表

| 编号 | 做法 | 实现要点 | 预期失效场景 |
|---|---|---|---|
| **E0** | Oracle | 枚举全部 $[u,v]$，检查四谓词，算 $D/m$ | 仅用于标签与正确性对拍 |
| **E1** | 全扫描 | 逐轨迹逐区间检查、算 DTW | 数据规模大时不可用 |
| **B1** | 先时间后空间 | 时间过滤得轨迹位图，再按空间包围盒筛 | 时间窗宽时位图几乎全 1 |
| **B2** | 先空间后时间 | R-tree/grid 取空间内段，再按时间过滤 | 空间范围大时退化为全扫 |
| **B3** | 先向量（post-filter） | 段向量 ANN 取候选，再验时间/空间，最后组装 episode | 约束选择性高时召回下降 |
| **B4** | 先约束（pre-filter） | 时间×空间分桶，桶内做 ANN 或线性扫描 | 桶小则 ANN 退化，桶多则构建贵 |

说明：

- B1/B2 的“过滤”只做一次，不迭代、不级联。
- B3/B4 的候选预算取固定默认值（如 top-$n=300$），不按查询调整。
- 不设“逐查询选顺序”“过滤感知遍历”“段级下界剪枝”这类基线；它们属于主体方案或工程优化，写进来会让比较失去意义。

## 4. 评测契约（精简版）

| 项 | 规定 |
|---|---|
| 数据 | Massive-STEPS 用户级轨迹；主实验 Istanbul 或 6 城合并 |
| 查询 | 采样 episode，$m\in[3,6]$；时间窗 1 天/1 周/1 月/1 季；$R\in\{\text{无},50\text{km},5\text{km}\}$ |
| 查询数 | 500（扩展 1,000） |
| $k$ | 10 |
| $\delta_\Delta$ | $\max(30\text{min},25\%)$ |
| 段划分 | 每次签到一段；停留/移动分段作敏感性 |
| 距离 | $\lambda=0$ 为主，$\lambda>0$ 作敏感性 |
| 召回 | 轨迹级 $\mathrm{Recall@}k$，$\lvert R^*\rvert<k$ 时分母用 $\lvert R^*\rvert$ |
| 违规 | 必须为 0，否则该运行无效 |
| 延迟 | 单线程、热缓存、3 次取中位数，报 p50/p95 |
| 额外成本 | 候选轨迹数、DTW 次数、索引字节、构建时间 |

## 5. 参数策略

- 每个基线的参数网格相同且很小：ANN 候选数 $\{100,300\}$；分桶粒度 $\{$城市, 城市×季度$\}$。
- 取该基线在网格上的最好结果报告；不报告“默认参数下的最差结果”。
- 网格、随机种子、硬件环境在附录取一次，正文只引用。

## 6. 与主体方案的分工

| | 基线 | 主体方案 |
|---|---|---|
| 目标 | 代表标准做法 | 新索引/算法结构 |
| 强度 | 默认参数、单一机制 | 允许新结构、证明与复杂度 |
| 论文位置 | 实验对比的参照线 | 方法与理论章节 |
| 判据 | 只需可信 | 需在相同候选预算下降低 DTW 次数或提高召回 |

主体方案必须回答的问题：在**同一 ANN 后端、同一候选预算**下，结构改动是否降低了精确验证次数或提高了 Recall；如果差距只出现在各自最优参数下，则不构成贡献。

## 7. 风险与对策

1. **稻草人质疑**：对策是每个基线都按实践中常见方式实现，并报告其最好结果；不隐藏更强的配置。
2. **基线过强导致贡献消失**：这是有价值的负结果；若标准做法已足够，说明问题不需要新索引，应重新选题而不是包装。
3. **参数不公平**：统一网格、统一后端、统一验证代码。
4. **结论预设**：本文只定义方案；没有运行结果前不写任何胜负。
