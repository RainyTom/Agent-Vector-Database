# 方向 08 方案状态：什么成立、什么被否证、相对基线在哪

日期：2026-10-29。用途：一次性看清当前方案、已测结果、失败的假设，以及"是否/如何超越基线"。

## 1. 一句话现状

**没有一个候选在端到端指标上超越公开基线；所有"超越"都发生在同后端自建基线或替代协议之间。** 三个看起来显然的修复（路由、可回收摘要、索引级 MVCC）都被实测否证或缩小。当前可交付的是一个**带实测常数的维护策略**，不是一个更快的新索引。

## 2. 当前方案（可交付部分）

**索引**：沿用 NodeANN 结构——每个直接绑定节点一个局部 hnswlib HNSW（小节点走精确扫描，阈值由微基准冻结：$T_{128}=1024$、$T_{1024}=512$），全部原始距离统一 `RawL2Space`。

**维护（本轮唯一的方案增量）**：

1. **移动协议 = 先插入后标删**（insert-then-delete）。异常窗口 1.5 µs vs 反向的 190 µs，**小 60–115 倍**；合并结果按全局 ID 去重（$O(k)$）。
2. **压实策略 = 死条目比例阈值**：当 $\delta>\delta_{\min}$ 且 $k_\delta(\delta-\delta_{\min})Q>c_r$ 时重建该节点索引。WIKI 实测 $k_\delta\approx82\,\mu s$/单位死比、$\delta_{\min}\approx0.11$、单节点 $c_r\approx40$ ms；全量重建与增量维护的交叉点 $\alpha^\*\approx0.62$（WIKI）/ $0.78$（D6 skew）。
3. **不做**：路由（见 §3）、可回收摘要（见 §4）、索引级 MVCC（见 §5）。

**明确不触碰全局结构**：属性变更只影响两个节点的局部索引；子树重挂只改指针（局部索引整体随节点移动，$O(1)$）；MOVE 的真实代价是依赖 DFS 区间的辅助结构重编号（中位 3,598 节点、p90 17 万），不是 ANN。

## 3. 成功：在这些对照上确实更好

| 结果 | 对照对象 | 数字 | 证据 |
|---|---|---|---|
| **B1 > B0**（同后端、同 recall=1.0） | 自建 NodeANN 基线 | SIFT 六变体 1.2–2.8× 延迟、10–34× RSS、2.8–6.1× 构建 | 01 方向 [report](../../01-directory-aware-acceleration/2026-10-29-exps/report.md) |
| **B0 在 WIKI 结构性不可行** | 自建基线 | hnswlib 每索引 65,536 把锁 ≈2.6 MB × 363,467 节点 ≈ 950 GiB；40 GiB 上限下 18/18 SIGKILL | 同上 |
| **插入优先 ≫ 删除优先** | 替代移动协议 | 异常窗口 1.5 µs vs 190 µs（热点 16 µs vs 967 µs） | 本文 §5 |
| **压实 > 不压实（延迟）** | 纯墓碑 | 44% 死条目时延迟 79.3 → 47.9 µs（回到 +11%） | [report](report.md) |

## 4. 失败：被否证的假设（带数字）

| 假设 | 实测结果 | 判据 |
|---|---|---|
| **C1：廉价摘要路由能省 item 访问** | oracle 上界 **99.4%**（≥10k scope），可达仅 **1.29×**（WIKI）/1.16–1.22×（SIFT bal）/1.01×（skew）；0.999 召回需访问 49.5%（WIKI 质心）到 99%（SIFT skew） | 预注册判据 "<20% 即关闭"，实际收益低于风险价值 |
| **层级贪心剪枝**（top-m 子节点） | ≥10k scope 的 ceiling recall = **0.0 / 0.9% / 1.5% / 4.8%**（m=1/2/4/8） | 直接否证 |
| **几何下界 $\lVert q-c\rVert-r$ 可作剪枝** | 覆盖率 8%（top-10 节点）/27%（top-1%）——三次实验中最差 | 与 d=1024 块剪枝 0% 的负结果一致 |
| **墓碑伤召回，需压实修复** | 召回不降反升：WIKI +0.7 pp、ef=8 +8.4 pp、D6skew 持平 | 直接否证；压实降的是延迟 |
| **可回收摘要（引用计数）值得做** | 陈旧位 35% 但探测只 +20%；主因是**桶粒度**而非陈旧度；精确计数要 15× 空间 | 缩小为"分辨率问题" |
| **epoch/版本化摘要** | age≤100k 仅覆盖 5.0% 真值；激进模式漏 93.6%，保守模式与 OR 逐位相同 | 买不到工作点 |
| **"只在属性值变化时更新摘要"能救 OR** | 纯重挂（无值变化）同样退化：FP 0.350 vs 0.351 | 反例 |
| **并发需要索引级 MVCC** | 插入优先 + 节点锁下异常 <0.03% 查询；真正成本是锁持有（热节点 +21–43% 延迟） | 未获证据 |
| **MERGE 冲突协议是研究问题** | 冲突合并规模中位 **6 个 item**、p90 38 | 降级为工程细节 |

**为什么还没测**：动态场景下的公平对比需要三件事同时具备——(a) 三基线的**动态版本**（PE 系列要定义属性变更下的 posting 维护）、(b) 同一更新流、(c) 同一质量口径（scope 级 GT 随更新变化）。只做 (c) 而不做 (a)(b) 会得出不可比的数字。

## 6. 要产出"超越基线"的结论，还缺什么

唯一的合并实验（已设计，未实现）：

**端到端 churn 实验**：同一进程内，`nodeann_research` 的 scope 级查询 + churn 更新流，三个对照臂：

| 臂 | 索引 | 维护 |
|---|---|---|
| A（本方案） | NodeANN 局部索引 | 插入优先 + 阈值压实 |
| B（PE-ONLINE 动态版） | 全局 hnswlib HNSW + 前缀 posting 维护 | 每次移动 $O(1)$ posting |
| C（PE-OFFLINE 动态版） | 全局 hnswlib HNSW + 祖先物化 posting | 每次移动 $O(t)$ 祖先更新 |

变量：更新率（0/10/20/50/80%）、查询/更新比、访问局部性（均匀 vs 热点 16 节点）。指标：scope 级 recall@10（每次 checkpoint 重算 GT）、p50/p95/p99 延迟、维护耗时、RSS、死条目比例。

**预计结论方向**（可证伪）：A 在"高更新率 + 热点"下胜出，因为全局索引的 posting 维护成本随 $t$ 增长而 A 是 $O(1)$ 局部的；A 在"低更新率 + 大 scope"下会输给 C（recursive 解析 9.7 µs vs 63 节点 fan-out）。

## 7. 诚实边界

- 三个否证都是在本数据/本实现下测的：WIKI（真实树、节点均值 5.34）+ SIFT1M 六合成变体（属性与几何独立或弱相关）。属性与几何强相关的数据可能改变路由结论（本次未构造）。
- hnswlib 的墓碑语义（删除点仅作导航）决定了"墓碑不伤召回"；换成物理删除/重建式索引（FreshDiskANN、Vamana RobustPrune）结论可能相反，不能外推。
- 并发实验只有 1 更新线程 + 1 查询线程；多写者与长事务未测。
