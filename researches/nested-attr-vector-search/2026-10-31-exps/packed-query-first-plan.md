# 查询效率优先：复用索引、暂停维护实验

**已实现：源码d4add37；[服务器精简任务](packed-query-first-server-prompt.md)、[实际运行证据](packed-query-first-local-report.md)。** 本文件是最新执行目标，旧完整矩阵只保留为历史设计。

## 1. 用户最新目标与旧任务的替换

用户明确：远端进展太慢，先把目标收敛为查询效率超过基线；复用已建立的资源，增删改操作先给理论可行性即可。本协议替代旧packed-server-prompt中的全矩阵、维护包络和1M推进要求，**不是推翻旧实测或删除维护实现**。

当前唯一性能问题：在已有数据单元、相同k和共同Recall层上，P-dfs或P-dfs-aware的完整查询延迟是否低于纯NodeANN。新颖性分析保留，但不再要求先完成node/shuffle消融、全生命周期实测或大N矩阵才能回答此问题。

- 暂停：maintenance、full repack、envelope、并发、长期稳态、额外数据生成、粗细目录/相关性全矩阵、自动SIFT1M。
- 保留：真实资格、真实图搜索、统一距离核、非法/重复检查、正确GT、实际Recall和e2e。
- 内存记录为辅助；构建记录一次，不要求先摊销全部维护成本才能承认静态查询优势。
- 复用既有组合索引是本次路线；不因原语是Trie/bitmap/分区就提前否定贡献。当前通过的是效率可行性门，不等于已经完成论文贡献验证。

## 2. 只运行最小矩阵

| 变体 | 索引 | 查询策略 |
|---|---|---|
| A-graph | 原纯NodeANN：非空direct目录一张图 | off、scan0，不新增规划或精确扫描 |
| P-dfs | 已实现B4096整目录DFS共享图 | cap，所有含eligible对象的块都搜索 |
| P-dfs-aware | **与P-dfs同一张驻留图** | E≤512精确扫描，否则同cap |

固定k10、M16、efConstruction200、efSearch20；每个变体3遍查询。总计9遍，不运行额外ef、B、布局或维护轨迹。预算20不是召回保证；全部实际Recall保留。

主要指标：非空query e2e均值、p50/p95/p99，macro/pair同时给出，empty单列。先报告双方同时达到的.99/.95质量层及精确实际数值；若候选Recall明显更低，不把较短时间叫同质量胜出。目标是耗时比<1，不再要求上一轮≤.80才能结束或开始别的阶段。没有更高Recall点时，本批次只说未取得同质量优势，不自行加预算追正。

P-aware获胜、P-cap不胜时，可以接受“组合方案含执行策略的查询效率超过纯NodeANN”，但不能声称合并机制独立获胜。那类论文归因在取得可用点后再补，不阻塞本轮效率目标。

## 3. 真正复用什么，不能假装复用什么

### 已有数据和GT

优先使用服务器已经准备好的同一真实数据目录、静态events.trace和GT tape。`run_packed_query.py --from-static DIR --name NAME`核对manifest的数据SHA、trace SHA和GT SHA后使用，不重新生成层级、不重新计算完整GT。只借用GT答案和分组，不混用旧计时。

若只有既有data与混合trace，可显式传入数据/trace：抽取已有前256条Q（旧输入不足可使用实际条数并披露），生成一次独立GT；不执行其中更新。不是新动态轨迹结果。

### 已构建索引

旧进程已经退出、且未saveIndex的图不能从CSV恢复；当前实现没有旧图的磁盘恢复接口。不能承诺“加载服务器之前构建但未保存的图”。

新增 `dynamic_triad --static-batch FILE`：每进程只build一次，随后多遍搜索共享**同一实际图**。A进程3遍；P进程6遍，cap/hybrid交替；P资格索引也只构建一次。9遍查询共2次build，而不是9次，P两种策略不重复建图。不做结果缓存、不复用GT当搜索答案。

schedule包含计数以及 `EF POLICY QUOTED_OUTPUT_PREFIX`；提前核查trace仅有Q，禁止任何更新或最终repack。各遍独立输出CSV、重置GT读指针和统计；保留实际索引。summary同时记录session建图来源与当前pass是否复用。build_s是同一session的来源，不将9份summary的build重复相加。

### 计时边界

这里是建图后warm/resident查询，三遍不是三次独立建图。为避免同时驻留两套大型图，A和P分进程按臂成组运行，不称此前串行交错轮换协议，也不称cold-start结果。GT验证、建图及输出写盘不在查询e2e内；资格、选块、距离、堆和合并仍全计费。峰值RSS为同进程所有遍的high-water，不是每遍独立峰值。

## 4. 维护先做理论分析：明确有效范围

记D为目录数，H为树高，b为局部物理图活对象/槽规模，m为受影响对象数，W为owner posting中的word项数，G(b)为本实现实际HNSW重建工作。这里只给结构成本及必要条件，不把未测延迟写成0，也不把启发式HNSW写成最坏O(log b)。

| 操作 | 当前机制与理论工作 | 可行性结论 |
|---|---|---|
| V/T属性修改 | 更新固定192个bitplanes中的变化位，64-bit字段宽度固定；对象元数据O(1)，不触碰几何图 | 与向量维度、祖先个数无关，不要求重建图 |
| M单对象移动 | 两个direct-owner稀疏word posting删除/增加，std::map为O(log W_old+log W_new)，loc不变 | 不迁移向量，不更新每个祖先ANN副本；后续搜索分散可能增加 |
| B批量移动 | 资格索引取得scope对象，再做m次M | 至少Ω(m)写入不能隐藏；不做m次图重插 |
| R重挂目录 | 资格树改父边并校验cycle；当前pack重算rank O(D)，runner还有受影响scope计数成本 | 与向量维度无关且不重建图；**当前代码不承诺O(log D)** |
| D | HNSW墓碑；live成员数组定位O(b)；墓碑到1/3同步重建，成本G(b) | 有界局部工作，不必全库重建；需要删除积累才能摊销重建，不保证每次都低延迟 |
| I/复活 | home/旧loc定位，正常HNSW插入；满槽压实，超过2target时局部split | split额外O(b log b)+两个子图重建；没有把重建成本抹掉 |
| 完整repack | O(N+D)布局元数据，加全部块G(b) | 是全量恢复手段，不是廉价单次更新；本轮不执行、不作为查询放行门 |

在块规模保持同一数量级、墓碑必须积累Θ(b)次删除后才重建的区间，局部重建的条件摊销为G(b)/Θ(b)每次触发相关删除；split也需要相应增量插入后才再次越界。不能据此推出对任意I/D交错、owner迁移或HNSW数据分布均有统一低延迟。旧的大owner图可以远大于B，不能一律把b写成4096。

因此目前可以支持的理论判断是：**频繁属性/归属变更与几何索引解耦；插删采用局部、有显式成本的维护。** 尚不能支持“所有操作已证明高效”“长期无需重排”或“已经实测动态胜出”。用户授权本轮不验证后两类性能，不意味着伪造其结论。

## 5. 当前执行顺序

1. 停止继续排队旧maintenance/扩规模任务；已经写出的结果保留，不删除失败点。
2. 优先选**一个已准备好的SIFT数据单元**，不重新制造四套数据；已有100k优先于新建1M。若SIFT输入未就绪，用已有真实WIKI/SIFT旧单元先跑，明确规模。
3. 复用已有static GT，跑2build/9pass。先得到最直接的质量—查询时间表。
4. 胜出就交付该可用点及分层，不要求先补全所有维护或创新消融；不胜也立即交实际差距和资格/距离/图调用归因，不自动扩矩阵。

本轮研究报告只需目标、已有输入、实际质量—时间、是否超过基线及理论维护边界。完整论文归因实验稍后单独立项，不让它拖慢当前效率验证。
