# “现有研究能解决查询，但我们要支持频繁属性更新”——这个定位能否成立

日期：2026-11-03。针对用户提出的重新定位：不争查询算法首创，改为在受限资源下支持属性频繁更新。本文只回答定位与可行性，不实现更新路径、不跑ANN查询对比。

## 0. 结论

**方向可辩护，但现在这句话不能作为贡献写进论文，也不能作为对外结论。**

三条硬事实：

1. **“支持属性更新”本身不是空白，而且已被当作主要贡献实测。** [EMA](https://www.alphaxiv.org/abs/2606.00734)（2026-05-30预印本，接收状态未核实）明确支持range/label/多谓词下的动态更新：删除1.3 s/1M、**属性-only修改2.5 s/1M**、patch 45.2 s/次≈全量重建371.1 s的12%，20%/50%阈值触发的实测在§5.4有曲线。数值range动态索引另有Peng PVLDB 18(10)、DIGRA、RangePQ+、ESF（正文未读，仅据EMA与MCI引用记录其存在）。所以“别人假设静态”是错误表述。
2. **当前代码完全没有更新入口。** `build_variant` 是一次性静态构图，没有insert/delete/relabel API；[main.cpp](../../../codes/dag-composition-methods/dag_merge/main.cpp)只建图后搜索。今天说“我们支持频繁更新”与代码不符。
3. **按现有构图逻辑直接做增量，单次成员变更并不便宜。** 本轮实测与成本模型（下节）显示：一次item换owner，定向刷新其祖先链约需 **3.15×10^5** 次距离计算（p95 5.10×10^5）；约为全量重建距离工作量的1.38%，**约73次更新就等于一次全量重建的工作量**。这还不含本地HNSW删除/插入与内存分配。

**因此可辩护的说法不是“我们支持频繁更新”，而是：“我们把谓词状态完全放在图外，因此更新不需要修补任何边摘要；能否在保持查询质量的前提下把维护成本压到可接受，是本轮要验证的假设。”** 这一条尚未实现、尚未测量。

用户提的“受限场景 vs 资源不受限场景”是对的方向，但必须指定**受限的是哪个资源**并在此轴上赢。现有证据里我们并没有自动占优：相对NodeANN，我们额外增加42%的有向边（4.02M→5.70M），**内存更多而不是更少**；相对一张M64全局过滤HNSW（level-0上限128）我们更轻。这一点必须先量化，否则“受限场景”只是措辞。

## 1. 本轮实测：静态重建与单次更新成本

单核（`taskset -c 3`），真实SIFT 168,937×128、1,929属性/2,040边、768个非空直属集合、M64/efConstruction200：

| 项目 | 数值 |
|---|---:|
| 两次全量构图 | 8.21 s、7.99 s |
| 有向边总数 | 5,697,634 |
| 其中本地边 / 连接桥 / 快捷边 | 4,019,094 / 1,652,935 / 25,605 |
| 最大行度 | 193 |
| portal条目总数 | 6,589 |
| 每个item的祖先属性数 | 均值4.21，最大11（多父属性103个） |
| 单次换owner：定向刷新祖先链 | 中位 315,392 次距离计算（p95 509,952） |
| 单次换owner：重跑受影响属性的桥循环 | 中位 1,994,808 个候选对（p95 3,561,760） |
| 折算：多少次更新≈一次重建 | 定向约73–78次；朴素约7次 |

**为什么祖先只有4个却这么贵**：代价不来自祖先个数，而来自祖先属性聚合的子树。桥循环对每个受影响属性遍历其直属与直接子属性的全部成员（`for source : {c} ∪ children(c) for u : members[source]`），根附近一次就是百万级候选对。所以“层级深=更新局部”在这里不成立：我们的DAG很浅（均值4.2），但每个祖先很宽。

对照EMA：属性-only更新是**微秒级**（2.5 s/1M），代价以周期性patch/重建出现。两者不是同一类账：EMA每次更新极便宜但会累积假阳性，我们的定向更新贵但不留陈旧状态。**必须用churn曲线比较，不能比较单次操作。**

## 2. 结构上真正可辩护的差异

EMA的Marker是**边上的属性位或**。原文§3.5原文：“updates the FT of reverse edges within one-hop neighbors by merging the new attribute information via a lightweight OR operation”。或运算只置位不回收（这是位运算定义，不是对作者实现的臆测），因此属性改值/删除后旧位留在边上，只能靠patch或重建复位——这正是其20%/50%阈值维护的结构性来源。

**我们的设计天然不需要修补边**：谓词资格由查询时`resolve_scope`从当前DAG算出（`allowed`掩码），图上的边和桥只表达几何邻接，不携带属性摘要。所以：

- 属性语义变化 **不触碰任何边**；
- 精确撤销由掩码计算保证，不依赖“或”的单调性；
- 没有假阳性累积，也没有为复位而必须的重建。

这与[TrieHI](https://www.alphaxiv.org/abs/2606.16903)的“不改变ANN布局”属于同一类正确性优势——**TrieHI已经有便宜更新**（MOVE元数据2.75 ms/op）。所以更新便宜本身不能算我们的新意；我们能争的是**便宜更新＋单张共享图的查询效率**这一组合是否成立。

诚实的当前状态：`allowed`路径已经满足“谓词与图解耦”，但**局部图成员变化还没实现**。一次换owner至少要：从旧owner的本地HNSW删除、插入新owner的本地HNSW、失效并惰性修复两个祖先链上的portal。第三项是唯一可能昂贵的地方，而portal本质只是**入口提示**：过期portal指向的item在新查询里会被资格门拒绝（不返回错误结果），只损失一次入口。因此有一条便宜路线：**portal作为可陈旧的提示，按需批量重算，而不是每次更新同步重算**。

## 3. 可检验的定位（尚未验证）

**主张草案**：在属性高频变更的层级多属性检索中，把谓词状态保持在图外（查询时掩码）＋共享单图查询，可以在不重建、不修补边摘要的前提下维持查询质量；代价是入口代表的可控陈旧。

要成立必须同时给出（缺一不成立）：

1. **更新成本与变更无关的项**：换owner的ANN侧成本≈一次删除＋一次插入，且不随子树大小增长；portal修复是摊销或按需的，不是每次更新同步。
2. **质量不随churn单调劣化**：0→100%重标注曲线上的Recall与QPS，与静态重建的差距有界；否则必须给出重建触发点。
3. **相对既有动态方案的位置**：同数据、同Recall下对比 (a) 全量重建，(b) EMA类“OR＋patch/重建阈值”模拟臂，(c) TrieHI式元数据＋NodeANN。
4. **受限轴明确**：内存（字节/向量）、单次更新p99、可接受停机时间，三者至少一个我们严格占优且能测。

**否证条件（先写死，避免事后找解释）**：
- 若定向维护的中位成本 > 重建成本/预期重建间隔内更新数，则该轴失效（按本轮数据，约73次更新＝一次重建，意味着重建间隔必须超过73次更新才有意义）；
- 若20% churn时Recall相对静态构建下降超过预设阈值（例如5个百分点）且无重建可救，则“不重建”不成立；
- 若相对TrieHI＋NodeANN在同召回下无查询优势，则组合贡献不成立。

## 4. 最小实验（未执行）

1. 实现唯一更新原语`relabel(item, new_owner)`：members/owner更新、本地HNSW markDelete+insert、祖先链portal标脏。
2. 两种维护策略：`sync`（同步重算祖先链，即本轮的定向成本）与`lazy`（portal按需/批量重算，更新路径只做本地图操作）。
3. 三类更新分开计：A类改名（应零成本、结果逐位不变）、B类成员、C类DAG MOVE/MERGE。
4. 指标：更新p50/p95按类、churn 0→100%每10%的Recall/QPS、峰值RSS、相对静态重建的差距、与(b)(c)两臂对比。

本轮没有运行这些；`sync`成本已由上表估出，`lazy`仅存在成本下界估计（一次删除＋一次插入），**不填收益数字**。

## 5. 证据与限制

- [构建与成本测量](../../../researches/nested-attr-vector-search/2026-11-03-exps/data/dag-update-cost/)：`build-cost.csv`、`update-cost-model.json`、`resources.txt`、`run-meta.json`。
- 程序：[measure_build_cost.cpp](experiments/measure_build_cost.cpp)、[estimate_update_cost.py](experiments/estimate_update_cost.py)。
- 限制：构建只跑2次；更新成本是**解析计数**而非计时，未含本地HNSW删除/插入、反向桥修复与分配；祖先链均值4.2基于本数据（多父103个），不能外推到深树；EMA数字来自其预印本§5.4，未复现；DIGRA/RangePQ+/ESF正文未读。
- 结论边界：**“我们能支持频繁更新”目前是待验证假设，不是已交付能力；本轮给出的是它的成本上界与失效条件。**
