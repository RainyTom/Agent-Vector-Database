# direct 慢是否因为探索更多节点？补齐原生工作量后的结论

## 结论

**要区分“多碰到不合格候选”和“多评分/多展开合格节点”。** 当前direct确实接触了更多包含被拒项的不同候选，但并未平均评分更多不同item或展开更多邻接表；单属性查询则多枚举约四分之一的邻接ID。因此不能把慢笼统归为“探索更多节点”，也不能把便宜的拒绝当成零成本。

在保持一张合并item图、共享frontier、原图/入口/k/ef不变的框架中，有进一步优化的可能，但本轮**没有证明direct整批同质量超越基线**。新做的静态owner分段候选少枚举18%–20%的邻接ID，却慢36%–52%，保留为负结果，未合入默认搜索。

## 1. 新增测量方法

沿用提交`9bb2836`的当前热路径。SIFT168,937×128 FP32、固定随机owner、M64/efConstruction200。仅direct、120个原有query/scope配对（101非空、19空），只测`k10/ef32`和`k100/ef128`。本轮不重测recursive，不改变既有`min(ef,eligible)`调用差异。

此前NodeANN的扩展/邻接字段为空，本轮补齐：

- 计数辅助函数保留原生上层下降顺序；底层调用原生`searchBaseLayerST<true,true>`，启用其已有metrics。
- `metric_hops`对应**邻接表读取/展开次数**，不是不同节点数；`metric_distance_computations`在这里累加的是邻接表长度，**不是实际距离调用**。
- 另用RAII距离hook统计实际calls、跨层去重的评分item和不合格距离，退出恢复原函数。
- 每张被搜局部图：新增诊断返回有序ID必须与原生`searchKnn`一致；外层归并继续使用原生(distance,external-ID)结果。
- 每query：新增诊断的距离总数和返回ID还必须与既有`NativeCounter + search_nodeann_topn<true>`一致。各局部图owner不重叠，因此distinct按图相加即query范围distinct。
- 正常计时仍调用原来的`search_nodeann_topn<false>`，**不安装hook、不启用新增底层metrics**。计数时间不当正常耗时。

DAG与NodeANN各用自己独立hnswlib/进程；NodeANN固定局部`n=k`。所有normal/count有序ID与每个计时pass的校验和均强制核对。输出逐query eligible、truth=min(k,eligible)、hits、返回数及上下层工作量，不以hits均值除以k冒充Recall。

## 2. direct整批：到底哪些工作更多

以下是101条非空查询均值；两个候选实现版本中计数完全一致。

| 指标 | DAG k10/ef32 | NodeANN k10/ef32 | DAG k100/ef128 | NodeANN k100/ef128 |
|---|---:|---:|---:|---:|
| 首次接触的不同候选item，含拒绝项 | 183.55 | 103.44 | 277.58 | 144.50 |
| 实际评分的不同item | 101.63 | 103.44 | 142.18 | 144.50 |
| 实际距离调用（含跨层重复） | 101.63 | 108.15 | 142.18 | 149.91 |
| 邻接表展开次数，上层+底层 | 26.56 | 32.56 | 77.16 | 86.79 |
| 其中level-0展开次数 | 26.56 | 31.42 | 77.16 | 85.64 |
| 邻接ID枚举次数，上层+底层 | 1,094.37 | 1,071.92 | 3,158.09 | 2,910.35 |

“首次接触”列：DAG当前拒绝缓存后，item资格检查只对该query首次遇到的item执行；所以该列含未评分的拒绝项。NodeANN选定的局部图全部合格、无删除/额外过滤，每个首次遇到item都会评分，该列等于其跨层去重评分数；不把硬件prefetch hint计为算法候选。

具体判断：

1. **如果“探索”指不同候选触达，是更多。** DAG约多77.5%/92.1%，其中约81.92/135.41个不同item被拒绝，不评分、不入ANN队列、不展开。这些item仍带来ID/seen/owner/allowed访存。
2. **如果指评分/距离，不是更多。** 平均不同评分item略少，实际距离calls也少；NodeANN上层与入口重复评分已单独区分。
3. **如果指扩展邻接表，平均也不更多。** NodeANN上层只有约1.15次展开、5.50条邻接；其底层仍为31.42/85.64次展开，高于DAG整图26.56/77.16次。不能仅把差距归为“NodeANN少走了很多高层路”。
4. **若指邻接枚举，DAG整体多2.1%/8.5%。** 这项并不因为拒绝缓存而消失；重复已拒绝item仍会在邻接行中出现并触发seen读取。它是负担，但计数无法给出该负担占整段时间的精确比例。

均值也不是每条query都少：

| 指标 | k10：DAG更多/相同/更少 | k100：DAG更多/相同/更少 |
|---|---:|---:|
| 距离calls | 0 / 5 / 96 | 0 / 0 / 101 |
| 不同评分item | 17 / 59 / 25 | 8 / 73 / 20 |
| 总邻接表展开 | 0 / 34 / 67 | 0 / 37 / 64 |
| 邻接ID枚举 | 88 / 0 / 13 | 92 / 0 / 9 |

因此不能从不同评分item均值更少推出每条query都更少。总展开是表读取次数，包含上层重复，不称去重扩展节点数。

## 3. 单属性和多属性：成本分布不同

| 子集 | (k,ef) | DAG不同评分item | NodeANN不同评分item | DAG总展开 | NodeANN总展开 | DAG邻接ID枚举 | NodeANN邻接ID枚举 |
|---|---|---:|---:|---:|---:|---:|---:|
| 单属性，88条 | (10,32) | 90.00 | 90.44 | 25.92 | 27.10 | 1,078.62 | 862.22 |
| 单属性，88条 | (100,128) | 128.36 | 129.02 | 72.99 | 73.94 | 2,986.22 | 2,403.65 |
| 多属性OR，13条 | (10,32) | 180.38 | 191.38 | 30.92 | 69.54 | 1,200.92 | 2,491.46 |
| 多属性OR，13条 | (100,128) | 235.69 | 249.31 | 105.38 | 173.77 | 4,321.54 | 6,340.31 |

单属性上两者评分和展开几乎相当，DAG每次展开枚举更多邻接，总枚举多25.1%/24.2%。但它不是“所有额外邻接都必然跨owner”：合并图还对局部有向边做对称化、排序并加桥；本轮不做逐来源时间分解。

多属性上，单frontier已经省下很多局部重复搜索和归并前搜索工作。direct多属性来自查询表达式命名多个直属属性，不是递归展开；不能把它说成一个查询属性的后代搜索。本批13条中，当前DAG正常时间也低于固定n=k NodeANN，但两格Recall为0.992308/0.997692，而NodeANN为1，仍不能宣称完整等Recall前沿胜出。

## 4. 同框架实验：静态target-owner分段邻接

为了测试能否消除拒绝邻接读取，构建一次新的静态表示：

`source item -> owner段目录 -> 该owner的原邻接IDs`。

每query按同一allowed掩码选择合格段；只用一个ANN frontier和一个best，不跑每owner top-k、不建query子图、不复制query图。

候选收集本行未见合格IDs后，按global-ID排序，恢复当前原行的评分顺序；排序和段选择都计入正常时间。程序强制逐query：候选与当前有序ID、距离calls、扩展次数一致，且`候选枚举ID数 + 跳过ID数 = 当前枚举数`。过程评分保序有控制流依据，但未归档完整评分/扩展trace，不称实测逐事件trace完全相同；seen与prefetch的访问顺序也可能变化。

做了两个实现版本，不是同一实现的独立重复构建：

- v1：每段24B，pending每行排序。
- v2：每段压为16B，只有选择多段才排序；单段内本就按ID排序。

| 版本 | (k,ef) | 当前µs/query | 候选µs/query | 候选变慢 | 邻接ID枚举减少 |
|---|---|---:|---:|---:|---:|
| v1 | (10,32) | 13.961 | 19.029 | 36.3% | 19.9% |
| v1 | (100,128) | 34.648 | 47.908 | 38.3% | 18.1% |
| v2 | (10,32) | 12.016 | 16.627 | 38.4% | 19.9% |
| v2 | (100,128) | 29.608 | 44.974 | 51.9% | 18.1% |

**两版都失败，不合入默认路径。** 该负结果不是“跨owner读取没有成本”，而是此实现节省ID枚举之后又引入了目录/选择/保序成本；不能反推出任意低成本跳过方案都无效。

可确认的新增负担：

- 共有5,697,634条边、1,701,194个owner段，平均每段约3.35条边；元数据很碎。
- v1的size-payload为64,970,696B（约62MiB）；v2为51,361,144B（约49MiB）。这是row offsets+IDs+headers的`size()*sizeof`，**不包括capacity余量、allocator、worker缓冲或仍驻留的原图/原生局部图，不是RSS或等内存服务预算**。
- 候选每query额外段资格检查约184.62/548.58次，另有入口资格检查9.31次；当前所有首次item资格检查总共183.55/277.58次。分段并没有简单地减少资格表达式的总次数。
- 逻辑ID枚举少，不等于硬件内存流量相同比例下降：还要读取段描述符、row目录、操作pending。没有硬件计数器，不分配cache/TLB/排序的独立百分比。

## 5. 当前框架有没有机会超过基线？

**有可能，但没有G或ef给出的无条件保证。** 目前已有两类证据：

1. 多属性OR子集确实减少了D、展开与ID枚举，说明共享frontier有实际收益；但质量、样本大小及n扫描限制仍在。
2. 单属性上D和展开已经接近native，继续单纯增加入口/预算很可能只加成本。若要反超，主要应降低每次访问、判定和队列维护的总成本，或以更好的导航真正减少需要展开的邻接，而不是只减少表面ID计数。

合理的下一项最小实验是：**同有序邻接、同起点、同资格门控的原生式执行路径/数据布局对照**，把入口、层次与拓扑从执行器比较中剥离。现有原生级别空间表示与DAG单图路由不矛盾，但前面的“按属性分块向量”或本次owner段目录都没有证明可免费回收差距，不能直接采纳。

本轮不同运行中，direct整批若只达到固定n=k NodeANN的速度，还需相对当前再降低约17%–37%的延迟。这个区间只是“达到所测参考需要的幅度”，不是预测收益、置信区间或理论剩余空间。真正宣称超基线还需要保持质量、重扫同格NodeANN局部n，并核算服务内存。
