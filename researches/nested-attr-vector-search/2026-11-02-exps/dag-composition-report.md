# DAG 组合顺序、邻居调整、高速路径与 bitmap 资格判断

目的：回答四个问题——(1) 子图按 NSW/HNSW 建好后，DAG 上按什么顺序组合；(2) 跨子图邻居怎么调；(3) 高速跳转边怎么设；(4) 为什么合并图在同质量下比 NodeANN 慢，以及 bitmap 能否加速属性判断。

结论先行：**当前组合顺序对图没有任何影响（距离优先的反向桥上限与插入顺序无关）；能真正减少工作的是出度剪枝与 visited 结构；高速跳转边在本负载上无收益；比 NodeANN 慢不是均匀现象，而是随合格集合规模放大的——小 scope 我们更快，中大 scope 慢 6–10 倍且召回下降。bitmap 用于 item 级资格判断时单查询净亏（构建 72–99 µs），只有多标签谓词或跨查询复用时才划算。**

## 1. 实验设置

- 输入固定：SIFT base 前 168,937 行 ×128 维，前 24 条 query；CCS DAG（1,929 概念 / 2,040 边），与既有 DAG 合并实验同一份 fixture，SHA256 见证据。
- 图：每个 owner 内部用 hnswlib 建 M=16/efC=200 的本地图，合并图保留全部原生 level-0 边（双向），再加 connector / jump 边。未改 hnswlib、未改 RawL2Space、无量化。
- **ef 已统一**：所有臂共用一个 ef 值，含义为单查询搜索预算。NodeANN 把 ef 分摊到各合格小图（`max(k, ef/G)`，G 为合格小图数），另保留旧的 per-graph 口径作对照。所有臂都记录实际距离调用数，因此残余语义差异可见。
- 计时：每个 (臂, ef, query) 预热 1 次、计时 11 次取中位数，再对 23 条非空查询取均值；`taskset -c 3` 绑核；GT 与 scope 解析不计时。
- **噪声控制**：`baseline`、`order_size_asc`、`order_size_desc` 三个变体构建出**逐边相同**的图，其 ef=512 延迟为 93.1 / 91.3 / 80.6 µs。即单次运行的均值噪声约 ±8–15%，小于该幅度的差异不解释。因此下文主要用**同 query 配对中位数比值**（消除机器漂移），而不是比较两次运行的均值。

## 2. 组合顺序：现有方案下顺序不可观测，强行引入顺序反而变差

组合分两阶段：先自底向上算 portal 集合（纯子树函数），再插边。插边阶段唯一的顺序敏感点是“反向桥”的接收上限：把一个父节点的桥接塞进目标节点时，节点最多保留 `cap` 条。

- 当上限按**距离优先**（保留最近的 16 个来源，当前实现）时，插入顺序被优先队列吃掉，`order_size_asc` / `order_size_desc` 建出**逐边相同**的图（connector 1,652,935 条，度 24.06，完全一致）。**结论：这一维当前是空的，不需要调 DAG 顺序。**
- 把它换成**先到先得**（保留最先到达的 16 个来源）后顺序才可观测，但质量下降：

| 变体 | ef=32 R@10 | ef=512 R@10 / µs | ef=2048 R@10 |
|---|---:|---:|---:|
| 距离优先（当前） | 0.8391 | **0.9565** / 93.1 | 0.9957 |
| FCFS + DAG 序 | 0.8087 | 0.9391 / 81.1 | 0.9739 |
| FCFS + 子树升序 | 0.8087 | 0.9391 / 75.9 | 0.9739 |
| FCFS + 子树降序 | 0.7913 | 0.9391 / 103.2 | 0.9783 |

即：**顺序敏感的实现都比顺序无关的距离优先差 1.5–2.4 个召回点**。可执行建议是保持距离优先准入（它同时免掉了顺序调参），不要为了“组合顺序”引入 FCFS 配额。

## 3. 邻居调整：出度剪枝是唯一稳定收益，portal/connector 数量无稳定收益

固定 ef=512（单次运行均值，噪声带见 §1）：

| 变体 | 平均出度 | 局部边/连接边/跳转边 | R@10 | µs | gate µs |
|---|---:|---|---:|---:|---:|
| baseline | 24.06 | 2,374,436 / 1,652,935 / 37,901 | 0.9565 | 93.1 | 93.1 |
| no_reverse（关闭反向桥） | 23.58 | 2,374,436 / 1,570,739 / 37,903 | 0.9000 | 82.0 | 209.4 |
| no_distributed（只有 MST+portal 边） | 14.62 | 2,374,436 / 57,240 / 38,438 | 0.8957 | 58.4 | 179.8 |
| portal4 | 23.48 | 2,374,436 / 1,584,818 / 7,625 | 0.9435 | 93.5 | 228.4 |
| portal16 | 25.39 | 2,374,436 / 1,749,331 / 165,451 | 0.9652 | 110.7 | 110.7 |
| portal32 | 29.13 | 2,374,436 / 1,890,312 / 656,027 | 0.9652 | 107.5 | 107.5 |
| connector2 / connector3 | 24.33 / 24.57 | — | 0.9565 / 0.9565 | 93.1 / 100.6 | 93.1 / 100.6 |
| reverse64 | 25.17 | 2,374,436 / 1,839,606 / 37,857 | 0.9609 | 95.9 | 95.9 |
| **prune16** | **15.05** | 2,542,815 / 0 / 0 | 0.9565 | 98.5 | 98.5 |
| **prune24** | **19.92** | 3,365,904 / 0 / 0 | **0.9696** | **86.9** | **86.9** |
| prune32 | 22.47 | 3,796,804 / 0 / 0 | 0.9696 | 111.3 | 111.3 |

解读：

1. **分布式桥接边（1.65M，占 41%）是召回的来源，不是延迟的来源**。关掉它，ef=512 的延迟从 93.1 掉到 58.4 µs，但召回从 .9565 掉到 .8957，低 ef 更差（.7913）。所以不能简单删掉。
2. **反向桥必须保留**：关闭后 .9000，且要靠 ef=2048 才回到 .9696。
3. **portal 数量不是免费杠杆**：4→16→32 召回到 .9652 封顶，但出度从 23.5 涨到 29.1，延迟随之上升。8 是当前负载下的合理点。
4. **出度剪枝（diverse cap）是唯一同时改善召回和延迟的调整**：prune24 把出度从 24.1 降到 19.9、召回从 .9565 升到 .9696、ef=512 延迟 86.9 µs；prune16 把出度降到 15.1 且召回不降。配对测量（§5）显示 `prune16 + dense visited` 相对 baseline 的中位比值 **0.899（18/23 条更快）**，ef=32 时 23/23 更快（0.839）。

⚠️ 剪枝在最大 ef 下反而变慢（prune16 842 µs vs baseline 691 µs），且 pruned 图在 ef=32 的召回仍 .8391 —— 剪枝没有改善低预算质量，只降低了每次扩展的成本。这是“每次扩展更便宜”而不是“图更好找”。

## 4. 高速路径策略：本负载上无可测收益

| 变体 | jump 边数 | ef=32 R@10 | ef=512 R@10 | ef=512 µs |
|---|---:|---:|---:|---:|
| jump0（无高速边） | 0 | 0.8391 | 0.9565 | 95.4 |
| jump1（当前：owner portal ↔ 子树代表） | 37,901 | 0.8391 | 0.9565 | 93.1 |
| jump2（+ 子 portal ↔ 父 portal） | 104,719 | 0.8478 | 0.9565 | 102.1 |
| jump3（+ 根 portal 全局 hub） | 182,621 | 0.8478 | 0.9565 | 81.3 |

三种策略的召回曲线完全相同，延迟差异全部落在 §1 的噪声带内（80.6–107 µs 的同图变体已经能差 15%）。**当前数据不支持“加高速边能减少搜索”**：jump3 的 81.3 µs 与 baseline 的 80.6–93.1 µs 重叠，不能算收益；而 jump 边让构建期多出 14 万条边。

需要注意这与“高速路径彻底无用”不同：本负载下合格集合是 DAG 下闭集，portal 入口已经直接落在目标子树里，跨层跳转没有可抄的近路。结论只覆盖本 fixture 与本搜索器。

## 5. 为什么比 NodeANN 慢：差距随合格集合规模放大，小 scope 我们更快

同一 ef 轴上，NodeANN 在 ef=32 就达到 R=0.9957（26.9 µs），合并图要到 ef=512（93.1 µs，R=0.9565）。但**这不是均匀的 3 倍**。按合格 item 数分桶（merged ef=512 对 nodeann_shared ef=32）：

| 合格 item 区间 | query 数 | 合并图 µs / R | NodeANN µs / R | 比值 |
|---|---:|---:|---:|---:|
| [0, 50) | 8 | **1.5** / 1.000 | 2.1 / 1.000 | 1.40×（我们更快） |
| [50, 500) | 7 | 27.4 / 1.000 | **4.7** / 1.000 | 0.17× |
| [500, 5000) | 6 | 225.3 / 0.983 | **23.2** / 0.983 | 0.10× |
| ≥ 5000 | 2 | 318.8 / **0.550** | **215.0** / 1.000 | 0.67× |

配对中位数比值（nodeann/merged）在 ef=32 为 1.318（23 条里只有 2 条更快），ef=512 为 1.035（11/23）——**均值差被少数大 scope query 主导**。典型例子：eligible=789 的 query，合并图 147.7 µs / 772 次距离，NodeANN 5.8 µs / 190 次；eligible=19596 的 query，合并图 356 µs 只拿到 R=0.50，NodeANN 305.5 µs 拿到 R=1.00。

机制（实测 + 计数，非推测）：合并图是**一次扁平搜索**，`ef` 是全局候选表宽度；合格集变大时它既照常扫邻接（每 query ef=512 时 723 距离 + 1,218 拒绝 + 3,786 重复边 = 5,727 次边检查），又因为候选表只有 512 而停止扩展，于是 3k–20k 的合格集上只覆盖 20%–60%，召回掉到 .50–.60。NodeANN 对每个合格小图各做一次有界搜索（本例 10 个图），单图规模小、保留原生层次，召回由“每图近似精确 + 归并”保证，工作随图数而不是随合格 item 数增长。

执行开销阶梯（baseline 图、ef=512、同 query 配对中位数比值；构建期不变）：

| 执行变体 | 中位比值 vs baseline | 更快 query 数 | 说明 |
|---|---:|---:|---|
| CSR 扁平邻接 | **1.335（更慢）** | 2/23 | 布局改动没有收益，反而更慢 |
| CSR + 边内联 owner | 1.03 | — | 与上同量级，仍无收益 |
| item bitmap 资格 | 0.985 | 13/23 | −12% 均值，但每 query +96 µs 构建 |
| **21 KB visited 位图** | **0.924** | **19/23** | 替换 675 KB visited 数组 |
| **prune16 + visited 位图** | **0.899** | **18/23** | 当前最优执行组合 |

所以“慢”可以拆成两块：**（a）每个距离要付出的边检查成本**（次数多 + visited 数组随机访问），可用出度剪枝与 21 KB visited 位图吃掉 10–20%；**（b）图结构需要更大的 ef 才达到同等召回**——这一块执行层优化解决不了，需要层次化或按 owner 分治的搜索。

## 6. bitmap 能否加速属性判断

单次判断成本（真实访问序列重放，��值，ns/check）：

| 实现 | 单 query 访问序列 | 构建成本 | ns/check |
|---|---|---:|---:|
| char 数组（owner→byte，当前） | 142 / 258 / 2,447 / 4,987 次检查 | 0 | 0.45–0.56 |
| owner 位图（1,929 位） | 同上 | 0 | **0.63–0.78（更慢）** |
| item 位图（168,937 位 = 21 KB） | 同上 | 72–99 µs/query | **0.36–0.49** |

- **单 owner 谓词下 bitmap 不划算**：当前 `allowed[owner[u]]` 已经只要 0.5 ns，换成位图反而更慢（多一次移位/掩码）；item 位图虽然每次判断快 20–30%，但每查询要扫全部 168,937 个 item 重建（72–99 µs），而整条查询才 26–95 µs，**净亏 1–3 倍**。
- **bitmap 真正起作用的地方是多标签/合取谓词**：合成 200k item × 8 标签、谓词为 2 个必需标签时，逐 item 扫标签 2.548 ns/check，预建 item 位图 0.308 ns/check，**8.3×**。此时构建成本可被谓词复杂度摊销。
- **visited 集合才是本实验里 bitmap 的实证收益点**：21 KB 位图替代 675 KB `uint32_t` 数组，配对中位 −7.6%（19/23 更快）。这不是“属性判断”，是同一思路用在可达标记上。
- **scope 掩码**：子树枚举 0.03–0.08 µs、位图 OR 0.03–0.04 µs，24 条 query 全部 mismatch=0。DAG 只有 1,929 个概念时两者都在 0.1 µs 量级，占查询 <1%，**不值得为它改结构**；概念数上万时位图 OR 的 `dirs × words` 优势才会显现（本实验未测）。

## 7. 结论与下一步

可以做：

1. 保持**距离优先**的反向桥准入，不做 DAG 顺序调参（顺序不可观测；FCFS 会更差）。
2. 把**出度剪枝到 16–24**（diverse 启发式）作为默认，配合 **21 KB visited 位图**：当前最优执行组合，配对 −10%，ef=32 时 −16%。
3. **不要加 jump 边**：本负载无收益、增加构建与密度。
4. 不要把 char 资格表换成位图；只有谓词变成多标签/合取时才用 item 位图，且要跨查询复用同一 scope 才划算。

还不能做（本轮未验证）：

- 剪枝在 ef=32 没有提升召回，说明图的**搜索质量**问题依旧。下一步应测“按 owner 分治 + 有界小图搜索”的混合执行（NodeANN 结构 + 合并图的跨 owner 连通性），以及给合并图加层（保留本地图高层，而非只用 level-0）。
- 大 scope 上合并图 R=0.55 是**质量缺陷**，不是延迟问题；任何均值延迟对比都必须同时给出召回。
- 未测：所有臂的邻接检查计数（NodeANN 侧无法在不改 hnswlib 的情况下计数，标为未测而非 0）、内存预算对齐、概念数上万时的 scope 位图收益、真实多标签 workload。
